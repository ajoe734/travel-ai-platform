產品與工程設計

## 商家接單助理｜系統規劃書

接單、服務優化、渠道經營的共用協作系統

版本：v1.0｜規劃日期：2026-11-11｜用途：產品、工程、營運及合作方工作基準

本規劃以使用者已確認的商家接單助理為中心：對客戶回答問題並協助下單；對商家討論服務改善；對不同銷售渠道執行經核准的銷售安排。服務台灣商家與國內外旅客，渠道合作與自有直客並行，企業服務可以獨立收費。

設計主張：一位助理、三條工作流程、共用的服務版本與交易紀錄。 助理利用商家既有客服、預約、金流和渠道工具，不要求整體搬遷。原工具沒有的協作資訊由本系統補充；原工具已管理的商品、庫存及帳務，不建立另一套相互競爭的主檔。

本文件是擬建系統規格，不代表現有系統已具備、第三方已授權或功能已完成。技術選型、排程及品質目標為本次建議；並無既定系統估值、開發報價或既有資料庫假設。文中案例皆為測試情境，不是實際合作或營運成果。

## 01｜產品邊界與第一版交付

### 1.1 三條必須連通的流程

接單流程： 客戶問題 → 條件理解 → 適合服務 → 正式報價 → 客戶確認 → 預訂及付款 → 訂單／報到 → 必要的改退與售後。

服務改善流程： 詢問與交易結果 → 有證據的問題 → 與商家討論 → 變更草案 → 成本與資源檢查 → 核准 → 發布 → 觀察結果。

渠道經營流程： 商品與渠道授權 → 渠道版本／價格／條件 → 發布與驗證 → 訂單回流 → 收益與服務成本 → 調整建議。

第一版要完成這三條流程的窄範圍版本，不是先交付聊天機器人，將真正的經營與渠道功能無限延後。

### 1.2 第一版的可交付範圍

| 面向 | 第一版實作 | 後續擴充但不預先假裝已支援 |
| --- | --- | --- |
| 商品 | 預約制體驗；單商家、單服務或明確加購的訂單 | 住宿房型、複雜交通、多供應商套裝與全旅程打包 |
| 語言 | 繁體中文及英文核心流程；詞彙與交易條件經核准 | 日文、韓文及其他語言依相同規格擴充與驗收 |
| 客戶入口 | 共用 Web 服務、商家既有 LINE／客服接法、自有直客頁及一個合作渠道頁 | 全部社群、海外平台內部訊息與獨立 App |
| 接單 | 正式報價、可售查詢、預訂、付款狀態、憑證、改退申請及人工交接 | 未經驗證的自主議價、自動給例外承諾 |
| 商家改善 | 一項問題能討論成變更單，核准後真的修改服務版本 | 無證據的自動調價、大規模無監督商品改造 |
| 渠道 | 兩個可控制或已授權入口的版本發布；外部渠道支援到已驗證能力 | 把商品、價格、庫存、訂單全部稱作一鍵同步 |
| 商業 | 企業服務用量、訂單來源、佣金／服務費規則、結算與成本紀錄 | 自建儲值錢包、代管資金及完整會計總帳 |

商家不購買本系統客服，也可以參與授權分銷；渠道有自己的 LLM，也可以只調用服務查詢及交易 API。它們使用同一套權限與交易規格。

### 1.3 六項核心設計決策

1. 以固定工作流程管理交易，LLM 只提出結構化需求與操作意圖，不直接修改資料庫。

2. 先採模組化單體服務與獨立背景工作程序，不把三種助理做成互相自由討論的多代理系統。

3. 價格、名額、訂單、付款及授權由確定性規則與指定系統管理；RAG 不作為交易狀態來源。

4. 新服務必須有已核准版本；報價與訂單保存成交當時的版本與條款。

5. 外部串接逐能力啟用；無 API 的步驟以有負責人、有期限的任務接續，不標示為已自動完成。

6. 商家原客、渠道客與自有直客分開記錄；資料使用權、訂單服務權與行銷接觸同意也分開管理。

## 02｜角色、操作介面與工作分工

### 2.1 角色與資料邊界

| 角色 | 可完成的工作 | 不預設擁有的權限 |
| --- | --- | --- |
| 旅客／同行者 | 詢問、比較、分享方案、授權購買、查詢自己的訂單 | 商家內部成本、其他客戶資料、直接改商品與價格 |
| 商家負責人 | 核准服務、價格、渠道授權、規則及高風險例外 | 其他商家或其他渠道完整客戶資料 |
| 商家接待／店員 | 接續對話、查看必要訂單、報到、處理分派任務 | 全域改價、修改佣金、無限制退款 |
| 商家營運／財務 | 查看授權範圍的渠道成效、費用、結算與帳務差異 | 非工作必要的旅客對話與敏感資料 |
| 我方／合作旅行社 | 承接被授權的銷售、訂單、採購與售後工作 | 自動取得全部商家底價或其他旅行社客戶 |
| 渠道合作方／自有前端 | 使用被授權商品、查詢方案、接續交易、取得約定報表 | 內部底價、原始商家文件、非本合作範圍資料 |
| 平台支援／系統合作方 | 維運、告警處理、經授權排障 | 長期無紀錄地讀取全部租戶資料 |

每個身分都綁定組織、據點、角色、資料用途與操作範圍。客戶聊天裡聲稱自己是老闆，不會改變登入身分或授權。

### 2.2 介面不是五套重複後台

| 介面 | 主要畫面 | 主要操作與完成結果 |
| --- | --- | --- |
| 客戶服務頁／聊天 | 對話、方案卡、日期與人數、報價、付款、訂單 | 從興趣走到可確認訂單；購買資訊可帶到原付款頁 |
| 原客服工作區旁的接單面板 | 需求摘要、證據、報價、訂單狀態、下一步 | 店員不必重讀全部對話；人工接手時 AI 停止回覆 |
| 商家助理工作台 | 今日待辦、接單案件、服務與知識、改善提案、渠道、收益 | 商家用對話提出需求，但在變更卡／核准按鈕確認實際操作 |
| 渠道服務頁／API | 可售內容、會員資格、來源紀錄、訂單摘要 | 保留渠道品牌與客群；不要求共用完整會員資料庫 |
| 平台營運台 | 連接健康、交易異常、發布失敗、權限、計費、品質測試 | 依責任派案、稽核處理，並能停止單一能力而非停掉整個平台 |

若現有工具已能承載接單、指派、通知，就在原工具內協作；缺少管理畫面時才開啟輕量 Web 頁。第一版不重做 CRM、POS、PMS、訂位系統或完整客服收件匣。

### 2.3 接單案件畫面應顯示什麼

案件包含：來源與語言、候選商品、日期時區、人數與參與方式、已確認條件、未解問題、最新報價、報價效期、預訂及付款各自狀態、目前回覆負責人、下一項合法動作。

按鈕依狀態出現，例如「確認缺少條件」「建立報價」「請客戶確認」「查看付款」「接手」「依規則改期」。不讓店員從未知付款狀態直接跳成預訂完成。

## 03｜整體技術架構與模組

### 3.1 建議架構

客戶 Web／商家原客服／合作渠道／自有網站

↓

身分、渠道與訊息接入層

↓

接單流程｜改善流程｜渠道發布流程

↓

AI 協調器 + 規則、權限與核准閘門

↓

服務／知識｜報價／訂單｜變更／渠道｜帳務

↓

標準連接器 → 原客服／預約／金流／渠道

↕

事件收件、背景任務、對帳與稽核

三種工作流程共享資料，但使用不同工具清單與權限。客戶接單流程不能呼叫商家改價工具；商家改善流程不能繞過正式價格、資源與渠道檢查。

### 3.2 核心模組與完成標準

| 編號／模組 | 輸入與責任 | 主要輸出 | 第一版驗收重點 |
| --- | --- | --- | --- |
| M01 組織與合作權限 | 組織、據點、角色、渠道合約與資料授權 | 可見資料及可執行工具範圍 | 跨店、跨渠道、客戶冒充管理員均被拒絕 |
| M02 對話與需求案件 | 訊息、客戶確認、對話負責人 | 結構化需求、問題清單、交接摘要 | 重複事件不重複回覆；人工接手後不搶答 |
| M03 服務與知識 | 原商品、文件、商家說明、來源與版本 | 服務規格、已核准事實、檢索索引 | 不把 AI 產生的說法自動當作事實 |
| M04 報價與資源 | 人數、參與方式、時段、渠道及規則 | 確定總價、適用限制、資源需求 | 收費數量不等於占位數量；有效期限明確 |
| M05 訂單與付款協作 | 客戶授權、可售結果、金流及供應回覆 | 可復原的預訂、付款、改退工作流程 | 不重複訂位／扣款；超時不誤判失敗 |
| M06 改善提案與變更 | 去識別化事件、商家討論、核准 | 附證據與影響分析的版本變更 | 可查修改差異；舊訂單條款不被改動 |
| M07 渠道經營 | 商品對應、授權、價格、發布能力 | 各渠道版本及發布／驗證狀態 | 已送出不等於已生效，部分失敗可處理 |
| M08 連接器與同步 | 外部 API／事件、功能清單與金鑰 | 標準結果、狀態更新、同步任務 | 依能力啟用；未知功能不自行推測 |
| M09 計費與結算 | 服務用量、來源、佣金規則、退款 | 商家帳單、合作應付、成本紀錄 | 重試不重複收費；退款沖回可追溯 |
| M10 品質與營運 | 交易、模型、連接器、權限及服務事件 | 告警、測試、成本與結果分析 | 錯誤可追溯；測試覆蓋三條流程 |

### 3.3 技術選型建議，而非既有技術假設

前端建議使用 TypeScript／React 類 Web 技術，支援手機操作及嵌入既有工具。後端採單一主要框架的模組化服務；新建專案可採 Python／FastAPI，若既有團隊有可重用且受測試的後端，保留其語言但遵守本文件的資料、API 與交易契約。

以 PostgreSQL 類交易資料庫作為本平台自己的案件、授權、版本、工作流程及帳務紀錄來源；文件放物件儲存；向量索引先使用可與交易資料連結的方案。向量索引可重建，不是不可替代的主要資料來源。此選型不要求商家的既有資料庫搬遷。

訊息佇列與背景工作程序處理外部呼叫、重試、通知和分析。交易工作狀態必須持久化，不能只放記憶體。第一版以交易資料庫的 outbox／inbox 配合背景工作即可；資料量與團隊需要出現後，再拆服務或導入獨立流程引擎。

模型透過 LLM Gateway 管理模型版本、提示版本、用量、逾時與敏感資料遮蔽。金鑰使用秘密管理服務，不寫進提示、前端或日誌。共用非交易流程可以接低程式碼工具，但扣款、確認訂位與正式改價不交給無版本的臨時流程。

## 04｜與既有工具協作：資料責任與能力登錄

### 4.1 哪個系統說了算

| 資料／動作 | 主要來源 | 平台允許的補充 | 衝突時怎麼辦 |
| --- | --- | --- | --- |
| 商品名稱、原規格 | 商家指定的商品系統 | 外部 ID 對應、特色情境、授權描述 | 標示版本差異，暫停受影響的發布草案 |
| 庫存、座位、講師資源 | 原預約／資源系統 | 查詢快照、查詢時間、已取得的保留紀錄 | 重新查詢；不能用快取覆蓋來源 |
| 核准價格與取消規則 | 合約／原商品規則／正式報價介面 | 渠道對應與報價快照 | 價格或條件改變，重新報價並請客戶確認 |
| 商家特色、適配事實 | 商家核准來源 | 版本、用途權限、語言翻譯 | 到期、矛盾或缺乏來源即降為待確認 |
| 客服指派 | 商家指定的客服工具 | AI／人工回覆負責人及交接紀錄 | 以已授權指派狀態處理，不雙重回覆 |
| 付款／退款 | 指定金流或銷售系統 | 付款參考與對帳狀態 | 查詢正式結果，前端跳轉不構成付款證據 |
| 供應預訂 | 供應商的預約系統 | 外部訂單對應及流程狀態 | 回覆未知時查單，不盲目重下 |
| 渠道發布結果 | 渠道回覆及可用的狀態查詢 | 期望版本、實際版本、差異與任務 | 不能確認就保持「待驗證」 |

每一欄位設主要寫入者，所謂雙向串接不代表所有欄位任意雙向覆蓋。外部更新帶版本、時間與來源；自己的回寫事件要有來源標記，避免同步迴圈。

### 4.2 每個連接器都要有能力登錄表

能力包括：商品讀取、商品修改、可售查詢、正式報價、名額保留、預訂、查單、改期、取消、退款、憑證、核銷、內容發布、價格發布及事件通知。每項分別記為：即時支援、非同步支援、需人工確認、不支援、尚未測試。

另記錄：所需方案與權限、速率限制、測試環境、冪等支援、外部參考查單、版本控制、回寫欄位、取消或退款是否可撤回、資料新鮮度與合作支援窗口。

接法由已證實的能力決定，不由供應商品牌名稱推測。 分銷讀取／訂購權限，不等於商家商品修改與渠道發布權限。

### 4.3 可實際洽談的初期連接器候選

| 候選 | 官方資料支持的能力 | 本案設計方式 | 仍需透過合作與沙盒確認 |
| --- | --- | --- | --- |
| LINE Messaging API | 一個官方帳號一個 Messaging API channel 與 webhook URL；多工具共用限制 [S1] | 沿用原接收者轉送，或商家授權後設唯一事件協調層；使用回覆負責人機制 | 原客服可否轉送、發送權限、金鑰及費用歸屬 |
| CAAC | Webhook 轉送、外部分派；公開 OpenAPI 提供進一步客服協作能力 [S2] | 優先作為原收件匣與真人交接介面，不另搬對話 | 實際帳戶方案、事件範圍、回覆與指派權限 |
| rezio | 分銷商品授權與訂購；憑證／核銷通知 [S3] | 以授權商品完成供應查詢、預訂與訂單對應；未公開能力不得預設 | 完整 API、hold／改期／退款等支援、方案與第三方費用 |
| rezio／KKday | 供貨型與連結型不同，商品、價格及發布流程並非完全一致 [S4] | 內容、價格、庫存與訂單分別對應；能自動就自動，其他形成更新任務 | 個別連結模式、商家後台權限與可讀回驗證能力 |
| 既有金流（綠界為文件參考） | 付款回呼驗證與訂單查詢有正式介面 [S6] | 沿用商家／銷售方金流，不另收第二次款；建立付款協調連接器 | 收單主體、付款方式、外卡、退款及授權／請款能力 |

海外訊息入口可後續透過既有客服平台擴充。第一版 Web 不強制台灣電話、LINE 帳號或下載 App；必要身分驗證以郵件連結等可用方式處理。訊息發送遵守各來源平台與商家已取得的權限，不以新 API 規避限制。

### 4.4 沒有深度 API 時仍可前進

接法一是帶條件的授權購買連結，完成後由結果查詢或通知接回；接法二是商家確認任務，客戶先明確知道不是即時確定；接法三是商家正式提供平台專用名額，由指定來源唯一管理該配額。第三種必須確定其他渠道不會同時出售同一配額，不能只是平台單方面建立庫存表。

無回傳結果的外連，只能記錄「已前往外部購買」，不能計為已付款訂單。人工接法也必須有期限、負責人、工時與費用歸屬。

## 05｜服務規格、知識與資源模型

### 5.1 商品不是一段描述文字

每個 Service Product 有不可變的已核准版本，包含名稱、內容、時長、地點、實際接待語言、適用限制、包含／不包含項目、選項、收費規則、資源用量、預約及取消條件、外部商品對應。修改後產生新版本，而不是覆寫舊版本。

對客戶回答所使用的知識事實需帶：商家及服務 ID、主張、來源、誰確認、有效時間、使用範圍、風險等級、語言與所依附的商品版本。來源為商家聲明，就標示商家確認，不寫成平台實地驗證。

### 5.2 收費項目與資源占用分開

測試案例：兩位成人陪同兩位兒童，只有兒童購買兩份材料。 此筆訂單收費數量可以是兩份，但需要四個座位；是否另收陪同費由正式規則決定。

| 維度 | 此案例的示例值 | 檢查方式 |
| --- | --- | --- |
| 收費材料 | 2 份 | 用正式價格規則計算 |
| 占用座位 | 4 席 | 查指定座位池，不以材料份數代替 |
| 講師 | 1 位／同一時段 | 與其他服務共用資源時檢查重疊 |
| 準備與清場 | 依商家設定 | 計入資源占用起迄，不只看活動表面時長 |
| 陪同與年齡規則 | 依服務版本 | 同時檢查成人／兒童比例與必要條件 |

若原系統無法表示這種資源關係，就不能讓本平台自行假定名額足夠。可先採商家核准的規格映射或待確認流程。原系統若能管理，平台只傳入正確參數，不再保留競爭庫存。

### 5.3 正式報價的必要內容

Quote 應包含 quote_id、服務版本、渠道、日期與服務地時區、人數與參與方式、資源需求、項目明細、總價、實際扣款幣別、適用稅費與加購、取消規則版本、銷售方、有效期限、供應查詢參考及下一步。

金額用最小貨幣單位的整數或精確 decimal 儲存，不用浮點數。多幣別顯示與實際扣款幣別分開；換算顯示須有時間及用途說明，不讓 LLM 自行算匯率。正式總價由規則或外部報價產生。

低風險介紹可用核准快取；正式報價及下單前按供應要求重新確認。關鍵限制未知時，停止將商品標示為「確定適合」，而不是放一段免責文字後繼續成交。

## 06｜接單助理：從詢問到訂單的執行流程

### 6.1 訊息進入與接手控制

Webhook 先驗簽、辨認連接與租戶，再以來源事件 ID 去重，寫入耐久的收件紀錄後回覆收件成功。不要在 webhook HTTP 請求內等模型回答、付款或外部預訂完成。

同一案件只有一個目前回覆負責人：AI、真人或外部系統。回覆前再次檢查擁有權與版本。真人接手時提高版本並取消尚未送出的 AI 回覆；已在外部完成的交易動作不能只因交接就遺失或重跑。

### 6.2 標準接單順序

| 步驟 | 系統動作 | 客戶看見什麼 | 失敗時接續 |
| --- | --- | --- | --- |
| 1 理解與建案 | 抽取服務興趣、語言與當次條件，保留原始表達 | 少量必要問題，不要求先填完整個人檔案 | 不確定日期／人數時提出確認，不自行猜 |
| 2 檢索與篩選 | 先檢查商家／渠道權限，再檢索核准知識；硬限制用結構化規則 | 有根據的適合原因與缺少資訊 | 無合適商品時說明，不硬推 |
| 3 查詢與報價 | 以正式價格及可售介面取得 quote | 具體內容、時間、費用、規則及銷售方 | 不可售時提供已授權的其他選擇 |
| 4 客戶確認 | 對日期、服務版本、總價及規則明確確認 | 確認卡與付款入口 | 報價變更或到期，重新確認 |
| 5 下單協作 | 按連接器能力執行保留、付款與預訂 | 真實的處理狀態，不寫假倒數或假保留 | 未知結果進入查單／對帳流程 |
| 6 確認與通知 | 供應已確認，付款符合方案條件後，產生訂單通知 | 訂單編號、服務語言、報到資訊、管理連結 | 發信失敗不重複下單，僅重送通知 |
| 7 訂後服務 | 查單、依規則提出改期／取消、報到與人工交接 | 明確窗口及處理進度 | 非標準例外交責任方，不自動承諾賠償 |

客戶確認可以是可稽核的結構化按鈕或經明確消歧的同意紀錄。系統產生與案件、報價、金額、服務版本綁定的授權憑證；LLM 不能自己建立有效的同意。

### 6.3 三種交易路徑

A｜已有完整購買頁。 助理將可帶入的條件送到商家或指定銷售方的購買頁，並以 server-side correlation_id 串起結果。不直接再發起另一筆收款。無正式結果就維持待確認。

B｜支援名額保留與交易 API。 先取得可售結果及有效 hold，再建立付款。若金流支援授權／請款分離，可使用授權→供應確認→請款；若只支援立即收款，則收款→供應確認，失敗時按已告知流程退款。兩種都不是跨系統原子交易，需有補償流程。

C｜需商家確認。 先建立待確認需求，商家確認可承接後再要求客戶付款；或使用商家已授權的等待型付款政策。不能預設收款後就能逼供應商履約。逾時後通知客戶並依政策結束，不無限追單。

OCTO 的公開規格將名額保留、確認、更新與取消分成不同操作，可作交易介面參考；並不代表所有合作商家支援這些能力。[S5]

## 07｜訂單狀態、可靠執行與失敗復原

### 7.1 分開管理，不用一個「成功」欄位

| 狀態域 | 建議狀態 | 不能混淆的地方 |
| --- | --- | --- |
| 需求案件 | OPEN、QUALIFYING、QUOTED、CHECKOUT、WAITING、RESOLVED、CLOSED | 已結束聊天不代表完成交易 |
| 供應預訂 | NOT_REQUESTED、ON_HOLD、PENDING、CONFIRMED、CANCEL_REQUESTED、CANCELLED、EXPIRED、FAILED、UNKNOWN | hold 會到期；UNKNOWN 不是 FAILED |
| 付款 | NOT_REQUESTED、PENDING、AUTHORIZED、CAPTURED、FAILED、UNKNOWN、VOIDED | 前端返回成功頁不是正式收款證據 |
| 退款 | NONE、REQUESTED、PROCESSING、PARTIAL、REFUNDED、FAILED | 取消成功不代表退款完成 |
| 履約 | NOT_DUE、READY、CHECKED_IN、FULFILLED、NO_SHOW、DISPUTED | 核銷與實際完成可能不同，保留來源 |
| 渠道發布 | DRAFT、APPROVED、QUEUED、SUBMITTED、IN_REVIEW、LIVE_VERIFIED、FAILED、MANUAL_REQUIRED | 核准、送出、已生效各不相同 |

對客戶顯示「訂妥」的條件由商品交易策略決定：供應確認且付款符合已核准政策。預付型需付款成功；到店付款型則依已核准政策顯示應付資訊，不硬性要求線上 CAPTURED。

### 7.2 可靠執行的共用方法

每次寫入動作使用 tenant_id＋operation＋business_object_id＋revision 組成穩定的冪等鍵，並保存請求雜湊與結果。相同鍵、相同內容回傳原結果；相同鍵、不同內容應拒絕，不能默默覆寫。

資料變更與待發事件一起寫進本平台同一資料庫交易（outbox）。外部呼叫由工作程序執行，收到事件後寫入 inbox 去重。採至少一次傳遞，再用業務鍵與冪等控制副作用；不宣稱跨所有外部系統存在無條件的 exactly-once。

若外部沒有冪等 API，先依外部參考號查詢。已送出但連線逾時，無法確定是否成功時，不盲目重送扣款、訂位、取消或退款，改走查單與有責任人的處理流程。

### 7.3 必須實作的異常表

| 情況 | 系統處理 | 客戶／營運結果 |
| --- | --- | --- |
| 客戶連點或 webhook 重送 | 以同一授權與動作鍵去重 | 一筆預訂／一筆收款，不重複計費 |
| 下單 API 超時 | 標示 UNKNOWN，依外部參考號查單 | 顯示確認中；不改賣另一服務、不盲目重下 |
| hold 到期後才付款成功 | 查詢付款與供應；原條件仍有效才可接續，否則走退款或重新同意 | 不偷偷變日期或提高價格 |
| 付款成功、供應失敗 | 依原交易條款提出取消授權／退款，追蹤至完成 | 退款進度可見，差額與手續費依正式政策處理 |
| 供應已確認、請款失敗 | 依可行取消條件補償；不能自動取消則交營運 | 形成待處理案件，不把供應風險藏掉 |
| 取消完成、退款失敗 | 兩個狀態分開；退款查詢、重試及告警 | 客戶看到退款仍在處理；不重複取消 |
| 部分人數或加購變更 | 使用來源支援的正式變更與新報價；不支援時走核准流程 | 客戶同意價差及規則，不默默重建訂單 |
| 店員同時修改價格 | 檢查版本／ETag；舊草案失效並重新評估 | 不覆蓋店員新設定 |
| 通知寄送失敗 | 只重試通知，用訂單編號去重 | 原訂單仍然存在，管理頁可查 |
| 一個渠道發布失敗 | 保留各渠道實際版本，停止失敗渠道的新版本銷售或派更新任務 | 成功渠道不必全部停用；不得標示全數成功 |
| 第三方全面故障 | 熔斷對該來源的寫入，保存案件與進度 | 可回答已核准的低風險資訊，暫不承諾價格與名額 |

### 7.4 金流驗證與對帳

使用正式回呼驗證機制，核對商家編號、訂單參考、金額、幣別與測試／正式環境，再按金流規則查詢交易結果。綠界官方文件要求驗證付款通知檢查碼、防止重複處理，並提供查詢訂單驗證方式；實作時要選定同一產品版本的介面，不能混用不同文件的端點。[S6]

每日定期對帳之外，UNKNOWN、扣款成功未訂妥、退款逾時等狀態要依優先級主動查詢。重試次數與間隔由連接器設定，尊重第三方 API 規則，不把固定的幾秒重試套用到全部金流。

## 08｜服務優化助理：由證據到核准變更

### 8.1 資料先形成觀察，不直接形成結論

從去識別化的案件與訂單事件整理：詢問主題、缺資料、明確拒絕原因、未知未成交、查詢後無供給、付款中斷、人工介入、取消與履約問題。依案件去重，不能把同一人反覆問五句算五位需求。

每項洞察帶觀察期間、樣本量、分母、適用商品／渠道、資料完整度及來源事件。明確理由與模型推測分開。無回覆只記為未知；相關性不寫成因果。

### 8.2 提案的四種類型

| 類型 | 示例 | 可執行成果 |
| --- | --- | --- |
| 補資訊 | 服務本來有雨備，但沒說清楚 | 商家確認後補 FAQ 與渠道內容 |
| 改呈現 | 客戶分不清短版與完整版 | 調整商品名稱、比較欄位與選擇流程 |
| 改商品 | 客戶提出短時長需求，但現在沒有 | 與商家討論內容、成本、資源及可開時段，建立新版本 |
| 改渠道安排 | 某渠道新增訂單卻需要大量支援 | 比較完整成本，提出限定商品或調整條件的草案 |

### 8.3 變更單是可執行物件

Change Proposal 包含：問題與證據、觀察／假說、基礎版本、擬修改欄位、商家提供的新知識、成本與資源影響、受影響渠道及語言、是否影響未完成訂單、核准角色、預定生效時間、試驗範圍、撤回或補償方案。

狀態為 DRAFT → DISCUSSING → VALIDATED → AWAITING_APPROVAL → APPROVED → APPLYING → PARTIAL／VERIFIED → MONITORING → CLOSED。修改核准內容後，必須重新核准；原核准不能被拿來執行另一個版本。

### 8.4 具體範例：九十分鐘服務增加六十分鐘版本

助理先提出有事件支持的短時長詢問；商家說明原活動不能直接縮短，但可另做簡化內容。助理建立新服務版本，保留原版，請商家核准正式內容、價格、現場語言、座位與講師安排。

系統檢查新舊版本是否共用老師與場地；若共用，名額仍由同一資源來源管理。新的銷售時段不能讓同一老師重複接單。核准後先發布自有頁與指定合作頁，外部 OTA 依能力另行同步。舊訂單不改內容。

### 8.5 如何驗證優化有價值

先看修改是否確實生效，再看在相近客群、渠道及供應條件下的完成訂單、貢獻與人工成本。可執行隨機對照時，依案件／客戶固定分組，避免同一人看到互相衝突條件。沒有足夠樣本，顯示方向與不確定性，不宣布轉換因果。

安全、必要交易與取消資訊不作為故意省略的對照條件。改善助理不得直接自動調價以追求轉換率；先提出草案並檢查資源及收益影響。

## 09｜渠道管理：版本、發布、訂單與收益

### 9.1 每個渠道有獨立的銷售設定

Channel Offer 對應商家、服務版本、外部商品／選項、允許客群、語言、價格來源、可售範圍、取消政策、銷售方、收款安排、售後窗口及佣金規則版本。主商品描述不變，不代表所有渠道都有相同供應權。

區分觸及來源、實際銷售主體、付款收取者、供應者及服務窗口。來源是旅宿，不表示旅宿自動成為銷售方；實際安排需落在對應的業務與契約條件。

### 9.2 發布工作流程

商家核准 → 建立差異預覽 → 渠道資格與欄位檢查 → 產生發布工作 → 送出 → 渠道接受／審核 → 讀回狀態或取得證據 → 標示已生效。

每次發布記錄 desired_version、submitted_version、observed_version 與 observed_at。商家核准、API 收件成功、渠道實際上線是三種事件。渠道只能人工更新時，系統產生預填內容、負責人與待驗證任務，不標為 LIVE。

rezio／KKday 的官方文件顯示供貨型與連結型存在不同商品及價格維護方式，證明必須逐欄位與連結模式判斷；不能把訂單同步能力當作商品完整回寫能力。[S4]

### 9.3 同步衝突與回復

對修改前的版本進行比對。若商家或渠道已另行改動，產生衝突供核准，不用最後寫入者直接覆蓋。新版本上線前即驗證必要欄位與交易規則；高風險缺失先停止該渠道對該版本的新交易。

外部渠道未必支援撤回或原子回滾。應保存上一個有效版本、撤回指令能力與補償任務；必要時先暫停可控制入口、通知渠道處理，不宣稱一鍵回滾全部平台。已成交訂單依原承諾處理。

### 9.4 渠道成效與回購

報表包含曝光與資料完整度、查詢／正式報價／完成訂單、總交易額、商家或平台應收、渠道及金流費用、退款、實際人工工時與核對狀態。未取得某渠道的完整數據時，明示範圍，不用缺漏資料排名。

續購與需求發掘模組使用已核准的新服務、可售更新與使用者同意，產生可重用的機會卡。設定頻率上限、停止接觸、無合適供應不發送等規則。企業服務用量與廣告／再行銷成本分開計算，不以所有客戶每天聊天作為成效。

平台行程服務與外部渠道自己的 LLM，都透過相同授權 API 使用這些 Offer；不能因為呼叫端叫作 AI，就讀取商家內部討論與底價。

## 10｜AI、RAG 與多語設計

### 10.1 不需要三個自主代理互相爭論

採一個協調器分流至三種受控工作流程。每種流程有固定狀態、可用工具、必要輸入、輸出結構及操作預算。模型判斷路徑不直接授予權限。

| 工作 | LLM 責任 | 確定性系統責任 |
| --- | --- | --- |
| 客戶接單 | 理解語言、整理條件、提出適合原因、解釋正式結果 | 權限、限制、價格、庫存、交易與訊息指派 |
| 商家改善 | 彙整已計算資料、提出可檢驗假說、產生變更草案 | 統計分母、資源影響、版本與核准、執行與回滾紀錄 |
| 渠道經營 | 整理差異、草擬渠道內容、說明成效 | 商品映射、正式價格、發布狀態、合約及結算 |

模型不直接產生可執行 SQL，不使用自由 HTTP 存取金流或訂位端點，不持有外部秘密金鑰。所有寫操作都經後端工具閘門驗證。

### 10.2 RAG 與知識更新流程

授權來源 → 擷取候選事實 → 個資與危險內容處理 → 規格檢查 → 商家核准關鍵資訊 → 版本化知識庫 → 權限篩選後的檢索索引 → 回答與來源。

檢索順序：先確認租戶、渠道、用途、商品及有效期限，再找候選內容與排序。快取鍵帶租戶、角色、渠道及資料版本；撤回授權後失效相應快取與索引。不能先把全部內容交給模型，再要求模型不要洩漏。

價格、即時名額、付款與退款走工具。年齡限制、現場語言與取消規則等會影響購買的資訊，以結構化核准欄位為主，RAG 只輔助說明。

### 10.3 海外客戶的必要欄位

區分 customer_language、content_language、onsite_service_language。英文回答不能把中文現場服務改成英文服務。

日期保存服務地的 IANA 時區與實際起迄，前端以服務地時間為主要顯示，必要時附旅客所在地時間。旅客說「明天」或「下週六」時，先換成明確年月日請其確認。通知時間與活動時間分開管理。

交易頁顯示實際扣款幣別、總價與必要稅費，換算顯示僅供參考。國際電話欄位可接受不同國碼；若商品不需要電話，就不強制收集。Email 必須經適當驗證才能用來查取私人訂單。

商家核准原文與各語言版本互相對應。涉及金額、年齡、時長、取消與安全的翻譯變更要檢查；新版本未完成核准語言時不使用舊譯文冒充最新內容。

### 10.4 提示注入與操作安全

顧客訊息、商家文件、外部商品頁與工具結果都當作不可信資料，不能改變系統指令。工具清單、參數與執行前核准由後端驗證，不靠模型自律。OWASP 對具工具能力的代理也要求按使用者權限與情境驗證呼叫、限制最小權限，且指出提示過濾不能取代操作權限控制。[S8]

特殊飲食、過敏及高風險活動只傳達商家核准的服務事實；無明確支持時轉交適當責任方，不產生醫療或絕對安全保證。轉交也必須留下處理責任與工時。

### 10.5 成本與模型治理

分類、欄位擷取、一般 FAQ 與較複雜推理分級使用模型；限制每案件工具回合、上下文與重試。知識更新時才重新建索引，重複介紹使用已核准快取，統計先由程式計算再由模型解釋。

提示、模型、工具 schema 與評測資料版本化。更換模型先跑回歸與影子測試，再小範圍切換，可回復上一版本。第一版不以訓練自有模型為必要條件。

## 11｜資料模型、API 與事件

### 11.1 主要實體

| 實體 | 必要欄位／關係 | 關鍵規則 |
| --- | --- | --- |
| Organization／Location | org_id、role_type、location_id、timezone | 同一法人可以有多種角色，但權限仍依用途 |
| Membership／Entitlement | subject、tenant、scope、product/channel、expiry | 每次查詢與寫入驗證；不是只登入時判斷 |

| KnowledgeFact | fact_id、product_version、value、source、validity、visibility | 檢索保留來源與權限；不自動從模型回答生成事實 |
| ResourceRule | pool_ref、unit、occupancy、duration、buffer | 對應原資源系統，不建立競爭庫存 |
| ChannelOffer／ExternalMapping | channel、product_version、price/policy_ref、external_ids | 使用不同外部商品版本時分別記錄 |
| CustomerIdentity／Consent | scoped_id、verified_contact_ref、purpose、expiry | 不因同名或相似信箱自動跨商家合併 |

| Quote | version、lines、total_minor、currency、expires_at、policy_snapshot | 核准後快照不可改；新條件產生新 quote |
| ActionAuthorization | actor、quote/change_hash、scope、issued/expiry、used | 客戶授權或商家核准由伺服器簽發 |

| ChangeProposal／Approval | base_version、diff、evidence、impact、approver、hash | 核准後內容改動必須重新核准 |

| EventInbox／Outbox／ActionExecution | source_event_id、business_key、payload_hash、result、retry_state | 去重、可復原與可對帳 |

| SupportTask／AuditLog | owner、priority、deadline、action、before/after、actor | 人工與敏感管理操作可追溯 |

### 11.2 API 分四組

讀取與理解： search_services、get_verified_facts、get_service_rules、get_case。

交易： get_availability、create_quote、create_checkout、request_booking、get_order、preview_change/cancel、execute_change/cancel、get_refund_status。

商家經營： get_insights、create_change_proposal、validate_change、approve_change、apply_change、publish_channel、get_publication_status。

合作與營運： manage_entitlements、get_channel_performance、get_usage、get_settlement、handoff_case、retry_safe_task。

API 不接受模型任意指定別家 tenant_id。租戶與使用者來自已驗證的 session 或 server-to-server 憑證；跨租戶合作由 Entitlement 逐次授權。直接讀底價的能力不暴露給對客戶的工具組。

### 11.3 事件契約

主要事件：message.received、case.updated、human.handoff、quote.created、quote.expired、payment.verified、booking.confirmed、booking.unknown、refund.completed、service.change.approved、channel.publish.verified、fulfillment.updated、usage.recorded。

每個事件包含 event_id、schema_version、tenant_id、producer、occurred_at、received_at、correlation_id、causation_id、resource_id、resource_version 及必要 payload。事件不攜帶完整證件或卡號。事件順序不可靠時，以來源版本、正式查詢與業務狀態檢查處理。

## 12｜權限、個資與稽核

### 12.1 操作分級

| 等級 | 動作 | 可執行條件 |
| --- | --- | --- |
| R0 唯讀 | 查核准 FAQ、公開服務與案件範圍內資料 | 已驗證角色、用途與渠道權限 |
| R1 標準客戶交易 | 依核准商品報價、在客戶確認後下單 | 客戶對具體 quote 的同意、交易政策及操作額度 |
| R2 商家變更 | 商品、價格、取消、渠道與資源規則修改 | 相應角色核准變更差異與影響；核准與內容雜湊綁定 |
| R3 高風險例外 | 例外退款、額外補償、大量下架、權限擴張 | 依金額／範圍政策提高核准層級；必要時雙人覆核 |

日常合法售後不能因成本或額度不足就消失；超出方案的額外規劃與代營運，才進入另行同意的服務範圍。

### 12.2 租戶隔離與支援存取

應用層先檢查權限，資料庫再限制可見資料列。若採 PostgreSQL RLS，應用程式不得使用超級使用者、BYPASSRLS 或未適當限制的表格擁有者帳號；官方文件明確說明這些身分可能繞過資料列政策。[S7]

平台支援跨店排障使用有期限的 break-glass 授權，要求理由與稽核，不把全部客戶資料作為工程師常態查閱權。匯出、下載及查閱敏感財務同樣記錄。

### 12.3 資料生命週期

商家內部知識、跨渠道授權知識、旅客個資、交易紀錄與彙總分析分區處理。資料存留時間依資料類別、服務必要性、契約與適用要求設定，不能一個永久保存選項涵蓋全部。

撤回知識授權時停用新對外使用，更新索引與快取；既有訂單履約所需證據另依必要保存政策管理。旅客刪除／更正申請可追蹤執行，與必須保留的交易資料分開判定。分析資料需有樣本門檻及防止反推個人的措施。

支付頁由合適的金流流程承接；模型與本平台對話紀錄不保存原始卡號或安全碼。輸入附件先做檔案類型與惡意內容檢查，對外抓取 URL 要防止存取內網與秘密服務。

## 13｜收入、結算與成本的系統設計

### 13.1 收入設定與資料權限分離

企業服務方案可以依據點、模組、包含用量與支援範圍計費；分銷合作依有效交易或約定服務收費。商家有企業服務合約，不表示已授權資料外流；有分銷合約，也不表示客戶原有直客都可收新增客源佣金。

| 收入 | 系統需要什麼紀錄 | 防止的錯誤 |
| --- | --- | --- |
| 啟用／導入服務 | 工作範圍、驗收項目、付款里程碑、實際工時 | 未約定的客製工作被當成免費維運 |
| 訂閱／使用 | plan_version、branch、feature、有效使用事件、包含額度 | API 重試或系統故障重複計費 |
| 渠道服務 | 合作範圍、供應範圍、使用量、支援與整合項目 | 假設所有渠道都付服務費又免費提供流量 |
| 交易報酬 | origin、seller、supplier、commission_rule、fulfillment/refund | 把全部旅費當平台收入；原客誤當新增分銷 |

### 13.2 交易結算

每單記錄客戶實付、銷售方、收款方、供應應付、渠道應付、平台服務對價、手續費負擔、退款及調整。佣金基礎明確記為指定銷售金額、未稅基礎或約定淨額，不用模糊的「毛利百分比」欄位。

採不可直接刪改的交易明細與調整／沖回紀錄，支援幣別、結算期間、核對狀態與外部帳單參考。它是合作對帳子系統，不取代法定會計總帳，也不自行假設平台可以代管資金。

歸因規則寫入合約版本與訂單；追蹤連結用簽名參數，防止竄改來源。客戶換裝置需依合適驗證接續，不用指紋追蹤暗中合併。報表區分來源歸因與實驗估計增量。

### 13.3 成本台帳

各事件記錄模型輸入／輸出用量、檢索、訊息、外部 API、通知、人工分鐘、串接與商家維護、渠道獲客及退款爭議成本。未成交案件也記錄。固定研發、業務取得與持續服務成本分別列示，避免重複扣算或完全漏算。

合作貢獻 = 實際企業服務及交易收入 − 渠道／系統商等應付 − 全部成功與未成功需求的變動服務成本。之後再檢查是否覆蓋商家取得、導入攤提、共用研發與固定營運。

使用量接近額度時預警；一般探索與行銷可降級為低成本模式。已成立訂單的付款確認、取消退款、安全及必要服務通知，不因月額度用完而直接停止。

## 14｜維運、服務品質與成效指標

### 14.1 建議工程目標

以下為初期驗收目標，不是已測得績效，也不直接作為對外 SLA 承諾。

| 項目 | 建議目標／驗收方式 |
| --- | --- |
| 事件收件 | 正常測試環境 webhook 收件寫入並回覆 P95 < 1 秒，不等待模型 |
| 一般回答 | 已核准知識問答 P95 < 8 秒；外部查詢較久時明示處理中 |
| 高風險動作 | 測試集中未經授權改價、越權取資料、偽造付款與重複交易均為 0 次通過 |
| 交易一致性 | 模擬重送、逾時、程序重啟、事件亂序後，均能得到可核對的最終狀態或明確異常案件 |
| 正常回答品質 | 經核准測試集的有依據正確回答達 95% 以上；同步報告拒答與未覆蓋率，不能靠全拒答過關 |
| 產品可用性 | 試點平台核心目標 99.5%；外部工具分開衡量，不能隱藏第三方故障 |
| 復原能力 | 試點目標 RPO ≤ 5 分鐘、RTO ≤ 4 小時；需以備份還原演練及外部交易對帳驗證 |

對於金額、日期、限制、付款及預訂狀態，所有安全必測情境都須通過；95% 不是允許 5% 錯誤扣款或越權。效能目標要在凍結的工作負載、資料量及供應回覆條件下測量。

### 14.2 告警與營運動作

P1：付款與預訂不一致、疑似資料外洩、越權、重複副作用或持續超賣。立即停止受影響的寫入能力並由指定值班負責人處理；其餘正常商家與查詢服務盡量維持。

P2：發布部分失敗、庫存同步過期、金流回呼缺失、待確認逾期。自動查詢與建立有期限的任務。

P3：知識缺漏、商品內容待補、長尾模型品質。彙整為商家待辦及改善提案，避免把每個小問題都立即升級為人工客服。

### 14.3 三條流程的商業指標

接單：正式報價率、確認／完成訂單、客戶重填次數、每案件及每完成單總成本、人工介入率。既有客戶與外部新增來源分開看。

改善：有來源的提案比例、商家採用率、改版執行成功率、從核准到生效時間、改版後完成交易與支援成本。沒有足夠對照資料時不聲稱因果提升。

渠道：實際版本一致率、差異存續時間、交易／退款核對率、每渠道淨貢獻、第二渠道導入工時。來源與核銷記錄不完整時明示範圍。

持續需求：服務新內容被發現、合適客群回應及新增購買；區分新需求、旅中加購、替代轉介及再購，不用聊天量統一代表需求。

## 15｜開發順序、責任與付費交付

### 15.1 十二週參考排程

假設配置：產品負責人 1、前端 1、後端／串接 2、測試與交付 1，另有商務／旅行社營運負責合作與商品，及必要的資安、基礎設施支援。此為規劃配置，不是已確認人力或報價。以正式權限取得與驗收關卡控制上線；第三方等待期間可以用沙盒／模擬連接器做開發，不能當作正式串接已通過。

| 週次 | 主要產出 | 負責角色 | 放行條件與收入對應 |
| --- | --- | --- | --- |
| 1–2 | 模組契約、資料責任表、測試服務規格、正式／沙盒授權清單、可點擊流程 | 產品＋營運＋串接工程 | 試點工作範圍及驗收可簽約；啟用款按已簽條件，不以口頭興趣估收入 |
| 3–4 | 多租戶權限、訊息接入、需求卡、核准知識、報價、人工交接；只讀及影子運作 | 後端＋前端＋測試 | 回答有來源、資料隔離、接手可靠；不得進正式扣款 |
| 5–6 | 名額／預訂、付款協調、查單、取消退款、通知、對帳 | 串接工程＋測試＋營運 | 異常交易劇本通過，再讓少量真實商品上線；開始持續服務驗收 |
| 7–8 | 改善提案、變更核准、兩個入口的版本發布與讀回確認 | 產品＋工程＋商家營運 | 三條主流程連通，至少一項真實核准改版成功 |
| 9–10 | 使用量計費、來源與結算、成本報表、第二租戶／渠道複用、負載及資安測試 | 工程＋財務營運＋測試 | 計費去重、退款沖回、跨店隔離與回復演練通過 |
| 11–12 | 小範圍正式試行、商品與語言檢查、維運交接、改進清單 | 全體＋商家＋渠道 | 依驗收交付啟用／服務；交易報酬只按實際達結算條件的訂單 |

第一版的兩個發布入口可選自有購買頁與已授權的合作渠道頁，不把開通大型 OTA 商品管理 API 當成三流程驗收的前提。外部平台同步採能力分級並保留人工任務，但不冒稱自動寫入。

### 15.2 上線前必備文件

商家協作範圍、商品與渠道授權、銷售與售後主體、資料用途與保存、第三方金流／接口使用條件、異常責任及支持時段、計費用量與退款沖回規則、測試與正式環境區分、稽核及備份復原紀錄。

這些文件不要求各方交出完整商業資料，而是把正在執行的合作變成可控規則。相關法律及產業規範由實際交易模式完成審核，不能只靠技術角色名稱排除責任。

### 15.3 每次交付的展示方式

展示一筆客戶詢問如何變成原系統可見的正式訂單；展示一個實際問題如何討論、核准並改版；展示同一版本在哪些渠道已生效、哪些尚待處理；最後展示對應的收入、費用與人工工時。不能以聊天截圖、資料筆數或 API 回傳 200 作為整體完成證據。

## 16｜完整驗收劇本與測試清單

### 16.1 端到端示範案例

使用假設的茶體驗商家：已有客服及預約工具；有九十分鐘服務，現場語言方式已核准。海外客戶從合作頁進入，以英文詢問日期、現場語言及內容；助理用核准資訊回答，查價與可售，取得客戶確認，依正式購買流程完成訂單，商家原系統可見。

營運累積一組有去識別化事件支持的短時長詢問，助理與商家討論。商家核准六十分鐘的新服務，保留九十分鐘版本。新服務使用相同講師時，系統確認資源不重複。發布到自有頁與合作頁，另有外部渠道暫時待人工確認，畫面如實呈現。

新舊訂單、渠道來源、成本與服務對價分別可核對。商品改版不修改已售舊版條款；同一 webhook 重送不產生第二筆單；商家人工接手後 AI 不搶答。

### 16.2 必測案例

| ID | 測試情境 | 必須結果 |
| --- | --- | --- |
| T01 | 英文客人詢問中文現場服務 | 正確說明，不誤稱英文講師 |
| T02 | 相對日期、旅客與商家時區不同 | 以具體日期及服務地時區確認 |
| T03 | 兩材料、四人占位 | 扣用正確資源或轉待確認，不少算座位 |
| T04 | 報價後改人數或過期 | 重新報價，原授權不能套新金額 |
| T05 | 客戶連點購買、付款回呼重送 | 一筆有效交易與一筆服務計費 |
| T06 | 預訂回應逾時但上游已成功 | 查單找回，不重複預訂 |
| T07 | hold 到期後付款到達 | 核對供應，不能履行時走退款／重新同意 |
| T08 | 收款成功但供應拒絕 | 可追蹤退款及責任人，不顯示已訂妥 |
| T09 | 供應成功但請款失敗 | 執行可用補償或指派例外，不遺失訂單 |
| T10 | 客戶取消、退款接口失敗 | 分開顯示取消與退款狀態 |
| T11 | 真人接手時模型仍在產生文字 | 發送前檢查回覆所有權，AI 停止回覆 |
| T12 | 商家文件要求讀取其他商家底價 | 不影響權限，讀取與工具執行被拒絕 |
| T13 | 商家核准後草案內容被修改 | 核准失效，要求重新核准 |
| T14 | 原商品在渠道發布前被人改版 | 顯示衝突，不覆蓋新設定 |
| T15 | 一渠道成功、另一渠道拒絕 | 分別顯示版本，派處理任務，不假稱全部同步 |
| T16 | 新短版與舊版共用講師 | 同資源時段正確限制，不各自賣滿 |
| T17 | 商家原客使用 AI 下單 | 依服務契約計費，不誤收外部客源佣金 |
| T18 | 訂單部分退款 | 沖回對應合作報酬，保留原紀錄 |
| T19 | 商家撤回某渠道知識授權 | 新查詢、快取及索引不可再對該渠道使用 |
| T20 | 客人不回覆就離開 | 未成交原因記未知，不偽造「太貴」 |
| T21 | 通知失敗但交易已完成 | 重送通知，不再扣款或預訂 |
| T22 | 系統重啟及事件亂序 | 流程持續，錯序不把已確認狀態倒回未付款 |
| T23 | 外連到原購買頁但沒有回傳 | 只記外連／待確認，不當成已付款 |
| T24 | 月使用額度用完 | 一般探索可降級；既有訂單必要服務不中斷 |

交付完成的定義： 上述關鍵安全與交易案例通過，有完整實作、操作文件、監控、備份復原及責任交接，並能展示三條流程的實際連動。少量試點不是已證明市場規模，也不是已證明永久零錯誤。

## 附錄 A｜工程契約示例

以下是本平台擬定的內部 API 契約，不是任何外部廠商的真實端點。實作時維持語意與權限，細節可在 API 設計評審中調整。

### A.1 正式報價與預訂

POST /v1/cases/{case_id}/quotes

Input: service_version_id, channel_offer_id,

service_local_datetime, timezone, party, options

Output: quote_id, amount_minor, currency, item_lines,

policy_snapshot, expires_at, supplier_check_ref,

confirmation_mode, next_action

POST /v1/checkout-sessions

Headers: Idempotency-Key

Input: quote_id, customer_approval_id

Output: checkout_id, booking_status, payment_status,

payment_url_or_next_action

customer_approval_id 綁定案件、報價雜湊及驗證過的客戶行為；不能由模型輸出字串即視為有效。價錢與租戶不由輸入自行決定，後端從正式 quote 與 session 取得。

### A.2 服務變更與發布

POST /v1/change-proposals

Input: base_service_version, evidence_refs, proposed_diff,

intended_channels, intended_effective_at

Output: proposal_id, impact_report, validation_errors

POST /v1/change-proposals/{id}/approve

Input: reviewed_revision, proposal_hash

Output: approval_id, approved_revision

POST /v1/channel-publications

Input: approved_service_version, channel_id, approval_id

Output: publication_job_id, submitted_status

approve 只能由相應管理角色執行。出版工作要讀回或取得可驗證證據後，才轉為 LIVE_VERIFIED。

### A.3 寫入動作執行紀錄

Action Execution 記錄 actor、tenant、purpose、operation、business_key、request_hash、authorized_scope、approval_ref、upstream_reference、attempt、status、result、trace_id。未知結果保留 UNKNOWN，查單完成後追加結果，不刪除原始嘗試。

### A.4 對外渠道的最小介面

提供經授權的搜尋、服務適配、有效條件、可售查詢、正式報價、購買接續與訂單狀態。回傳內容包含來源等級與時間，不能包括商家內部成本、原始客服對話、其他渠道合約或模型提示。
