## 商家接單助理

從回答與建議，進入案件處理與營運執行

v1.1｜2026-11-11｜搭配《商家接單助理系統規劃書 v1.0》使用

本增補保留已確認的產品方向，補足語音預訂、實際客訴處置、數據驅動的商家討論、素材索取，以及核准後的渠道商品與訂單操作。它是擬建規格，不代表已完成程式、商家授權、電信接入或第三方串接。

完成一項工作，不是生成一段回答，而是執行必要動作、取得可核對結果、通知相關人，並留下後續責任。

## 01｜四個處理角色，一套案件與執行核心

「角色」代表工作責任與授權範圍，不代表必須建立四個會互相自由指揮的獨立代理。初期仍沿用一個協調器、共用資料與受控工作流程。

| 角色 | 真正可以完成的工作 | 結案／完成證據 |
| --- | --- | --- |
| 接單專員 | 以文字或語音回答、確認條件、查價查位、送出預訂、引導安全付款、交付確認。 | 原預約系統的有效訂單與正確付款條件；通知已送出或另有追蹤。 |
| 售後與客訴專員 | 查訂單與成交承諾、收集事實、提出選項，依政策改期、重送憑證、取消或退款。 | 補救動作有正式結果；退款未完成、顧客仍有爭議時不偽裝已解決。 |
| 服務企劃與素材協作 | 依數據提出假說、向經營者追問、收集圖片／影片／語音，完成商品與服務變更草案。 | 有證據、成本與資源影響，素材用途已核准，產出可執行版本。 |
| 渠道與訂單營運 | 按授權建立／修改商品、上架／下架、管理銷售條件、接單、改退、核銷及對帳。 | 渠道實際版本與外部訂單可核對，部分失敗仍有負責人及期限。 |

### 每個案件都需要「下一步」

案件須記錄目前負責角色、下一個可執行動作、等待誰、期限、允許成本及完成條件。聊天結束不會刪除未完成工作；人工接手不會遺失已送出的交易。

### 授權讓助理真正做事，而不是每一步都請示

商家事先核准標準接單、符合政策的改期、憑證重送及限定補救規則。符合條件時自動執行；需要商家新判斷的價格、服務承諾、商業合作或重大爭議才要求核准。

客戶同意、商家政策授權、外部系統權限是三種不同依據；只有其中一種並不代表可以交易。新服務核准也不等於可以追溯修改舊訂單。

範例：符合已核准取消政策的退費，驗證身分與訂單後可自行辦理；不是一遇到「退款」就轉真人。

## 02｜語音入口：電話、網頁通話、語音訊息分開接

| 入口 | 建議接法 | 不應混淆的地方 |
| --- | --- | --- |
| 商家電話來電 | 既有門號／總機的授權轉接或 SIP 接入；電信／總機把音訊交給即時語音服務，後端處理工具與訂單。 | 店家門號、轉接費、錄音設定及真人轉接須實測；有語音 API 不等於可直接接台灣任一門號。 |
| 官網即時語音 | 網站按鈕開啟 WebRTC 語音會話；畫面同步顯示日期、方案與報價卡。 | 訪客可用語音交談，但付款與敏感確認仍走正式安全流程。 |
| LINE／其他語音訊息 | 取得已授權的音訊訊息，轉錄或多模態理解，再以文字／音訊及商品卡回覆。 | 這是非即時留言，不是直接接聽 LINE 原生通話。不得把兩者視為同一已取得能力。 |

### 主路徑

電話／Web 音訊 → 語音會話控制 → 身分與案件對應 → 接單或客訴流程 → 工具執行與結果查核 → 語音回覆＋必要文字憑證。

即時語音層可以先採現成服務，保留替換能力；業務規則、工具授權、正式交易與持久化狀態留在本平台。OpenAI 的官方語音文件支援 SIP／WebRTC 與伺服器側控制；這是實作選項，不是限定採購或已取得電話接入。[R01][R02]

### 電話流程的必要細節

接通時告知 AI 身分及適用的錄音／轉錄處理方式。可不保存原始錄音而只保留必要結果；實際告知、保存及服務地區要求由上線配置確認。不得以聲紋或來電顯示單獨授權退款與商家管理操作。

電話付款優先使用安全付款連結；客戶不能使用連結時，轉至已支援且核准的其他收款方式或真人流程。不要求客戶向 AI 唸卡號與安全碼，也不把敏感卡資料寫入逐字稿。

LINE 官方文件確認可依 webhook 的 message ID 取得音訊等附件；收件後必須驗簽、去重並依用途保存。它不證明原生通話可由這個介面接聽。[R03]

## 03｜語音預訂：聽懂、確認、執行與接續

| 步驟 | 執行規格 | 可核對的結果 |
| --- | --- | --- |
| 建立與接續案件 | 新客建案；既有訂單先用核准的驗證方式連結。電話與文字只能在驗證後對應，不依同名猜測。 | 同一需求維持同一案件及訂單關聯。 |
| 辨認與修正 | 擷取服務、年月日、服務地時區、成人／兒童及選項；聽不清楚只重問必要欄位。 | 關鍵欄位有原始片段與確認狀態。 |
| 查詢與覆誦 | 透過原系統查價查位，覆誦日期、人數、內容、總價及主要條件；網站同時顯示確認卡。 | 客戶同意綁定有效報價版本。 |
| 執行與付款 | 依 v1.0 交易策略建立保留、付款與預訂。一次語音會話可用多個工具，但每個副作用獨立受控。 | 外部訂單及付款狀態，而非語音說了「完成」。 |
| 交付與後續 | 用客戶核准的聯絡方式送訂單及報到資訊；需要真人時附摘要交接。 | 通知、接手及未完成任務都有追蹤紀錄。 |

### 打斷與改口，不可以變成錯單

客戶在聽到「週六」時改說「不是，是週日」：停止舊語音輸出，提高案件版本，取消尚未執行的舊報價／動作。已對外送出的動作先查結果，不能把取消音訊當成交易已撤銷。

只有正在審閱的完整報價被客戶明確同意，才產生交易授權。「嗯」「等等」「算了」或沉默不應自動解讀為同意購買或取消已成立訂單。背景談話也不作為管理指令。

### 斷線不是結案；轉接指令送出也不是已接手

已取得明確授權且開始的交易，依流程核對並通知；未授權的交易不可因為掛斷而繼續下單。重撥後經驗證接續，不重做第二筆。支援時使用暖轉接或帶摘要交接；沒人接時提供可用的後續窗口與進度，不能假稱真人已接手。

官方 SIP 轉接文件說明，REFER 接受只是將轉接要求交給下游電話服務；真正接通結果仍要由電話／總機事件確認。[R01]

## 04｜客訴專員：從接住問題到完成補救

目標是執行可處理的售後工作，不是只做情緒安撫、分類或寄出「已轉專人」。客戶即使無法立即驗證，仍可陳述與建立案件；涉及私人訂單查閱及修改，再完成必要驗證。

| 工作 | 系統需要執行 | 結果與界線 |
| --- | --- | --- |
| 收件與識別 | 記錄問題、客戶期待、是否有當下安全疑慮，連結原訂單。 | 接住客戶而非反覆索取相同資料；安全或人身事件立即通知值班責任人。 |
| 查明事實 | 調出成交當時的商品、條款與渠道頁面快照、付款、現場紀錄及先前處理。 | 客戶陳述、商家紀錄與已確認事實分開；不能拿新版條款處理舊單。 |
| 提出可行處理 | 依政策產生改期、補發、取消、退款或其他已授權方案，說明時程與影響。 | 不擅自承認責任、要求放棄權利，也不以刪除負評交換合理處理。 |
| 執行補救 | 驗證授權與客戶選擇，預覽差異，操作原系統並查結果。 | 渠道收款的訂單由有權的一方處理退費，不另外重複退第二次。 |
| 追蹤及結案 | 追蹤供應、金流、憑證與通知；檢查未完成補救，必要時重新開案。 | 退款處理中不算已退；客戶未回覆不等於滿意；保留結案原因與再申訴入口。 |

### 案件狀態與補救動作分開

案件：OPEN → CHECKING → WAITING_FOR_CUSTOMER／MERCHANT／CHANNEL → RESOLVING → RESOLVED → CLOSED；另有 ESCALATED、REOPENED。補救動作各自保存 DRAFT、AUTHORIZED、SUBMITTED、PENDING、SUCCEEDED、FAILED、UNKNOWN。

退款／改期動作成功，與客戶爭議已解決是兩件事。案件不得為了提高自動解決率而提早關閉；重複來電回到原案，新增事實以追加方式保存。

### 立即可自動處理的標準例子

查單與補寄確認、已核准範圍內改期、符合取消規則的退款、商家已預先授權的有限補救。重大人身事件、爭議事實、契約解釋或超出授權的和解轉交適當責任人，但 AI 繼續整理證據與追蹤下一步。

## 05｜授權設計：日常可執行，重大決策可控

| 權限層級 | 可採用的工作規則 | 執行條件 |
| --- | --- | --- |
| 預先核准的日常操作 | 標準接單、發送正式資訊、按規則改期、處理明確可退項目。 | 身分及訂單範圍正確；資料未過期；客戶已確認必要變更。 |
| 預先核准的補救政策 | 商家按原因碼、商品、渠道、金額或比例及期限設定可用方案。 | 可用餘額、累計處理、爭議付款及其他補償一併檢查；額度原子更新，防止雙渠道同時核發。 |
| 商家本次核准 | 新商品、調價、補救例外、批次下架或渠道商業條件變更。 | 核准綁定變更版本、欄位、影響、渠道、期限與費用；內容改動則重新核准。 |
| 專責人員判斷 | 人身安全、法律爭議、資料外洩、疑似詐欺、無法確認授權的不可逆動作。 | 交接摘要、證據、下一次更新期限及負責人；不得只丟進無人處理的佇列。 |

### 補救政策最小資料

policy_id／version、適用商品與渠道、原因碼、可選補救、計算規則、單案與累計限制、幣別、有效期間、需要的證據與客戶同意、可執行角色、原退款路徑、超出範圍的負責人。金額未核准時不自行填入示例額度。

這裡的限制是「AI 可自行執行的授權範圍」，不是顧客實際可獲得處理的上限。已成立訂單的必要售後不得因企業服務額度用完而直接停止；超出自動授權則升級處理，不是拒絕或關案。

### 讓授權減少摩擦，而非製造簽核

同一份已核准政策可以處理多筆符合條件的案件；商家可以一次核准一組商品、語言與渠道的變更。只有實際超出範圍或版本已改變才再次請示。低風險純草稿可以自動產生，但草稿不代表公開發布。

任何角色都不直接持有可隨意操作全部租戶的工具。後端執行前再次檢查權限、參數及核准，防止客戶或附件內的文字擴大操作權。這與 OWASP 對代理最小權限及高影響動作完整性的建議一致。[R06]

## 06｜用數據提出調整，而不是把推測寫成結論

分析由可重現的統計查詢提供數字，LLM 解釋觀察、提出待驗證假說並與經營者對話。來源、期間、分母、資料缺漏與商品版本都要可追查。

| 觀察資料 | 可以提出的建議 | 必須同時檢查 |
| --- | --- | --- |
| 詢問與明確未成交原因 | 補充常見問題、改善方案比較、討論短版或不同時段。 | 按案件去重；沉默與離開記為未知，不由語氣推定原因。 |
| 客訴與改退 | 檢查誤導描述、報到流程、語言落差與履約安排。 | 使用成交時版本；客訴件數需對照完成服務數與嚴重度。 |
| 渠道完成訂單與費用 | 檢查商品適配、呈現、銷售範圍及渠道條件。 | 扣除佣金、退款、金流、人工及補救；資料不完整不直接排名。 |
| 資源與服務成本 | 討論不同內容、材料、時長及可開時段。 | 短版不必然更有利潤；共用老師、座位與準備清場時間不能重複出售。 |

### 一張有用的建議卡

標題：是否新增短版服務？／依據：多少個獨立案件明確表示時間限制／未知：是否接受新價格與內容／方案：保留原版、另設短版／需商家提供：可省略內容、實際工時與資源／驗證：限渠道或時段試行，觀察完成訂單、淨貢獻及客訴。

尚未有足夠資料時，助理可以協助討論商品，但必須標示「商家構想／測試假說」。同一批詢問多不等於需求規模已成立，某項內容被引用與成交相關也不等於因果。

### 主動觸發與互動頻率

建議觸發包含：同一問題反覆出現、已確認的承諾落差、特定渠道更新失敗、商家指定的定期經營檢視。頻率與提醒預算可設定；低優先事項合併成少量待辦。急件立即派案，例行素材不逐條打擾。

驗證先看：改動是否真的上線，再看效果。可做對照時固定分組並保留必要資訊；無足夠對照則說明關聯與不確定性，不宣稱成長由 AI 造成。

## 07｜主動向經營者取得素材，並整理成可用資產

助理不是丟出「請補齊資料」表單，而是在每個改善提案裡，根據已知缺口，只索取完成這項工作需要的材料。先檢查已授權素材，避免重複索取。

| 缺口 | 助理向商家的具體請求 | 收件後的工作 |
| --- | --- | --- |
| 內容與流程不清楚 | 「請用一段語音說明這個版本從報到到完成有哪些步驟；哪些項目不包含？」 | 整理流程與候選事實，分開保留原話、草稿、核准結果。 |
| 接待語言有落差 | 「請確認現場能使用哪些語言；可否提供現有說明卡與示範方式？」 | 同步建立客服回答、商品說明及訂後通知的修改草案。 |
| 缺實際活動照片 | 「需要工作區、操作過程及完成品的照片；請確認拍攝者、使用權及可公開範圍。」 | 檢查品質、人物與權利；依渠道規格裁切和編排，保留原件。 |
| 新增服務缺規則 | 「請確認可開時段、材料、人員、座位、準備清場與正式價格。」 | 形成結構化服務草案及資源衝突檢查，不由模型猜定價。 |

### 商家可以用原本方便的方式提供

支援文字、語音、照片、短片、文件與已授權連結；在原客服或管理工作區接收，並綁定 proposal_id／material_request_id。收到後回覆「已具備什麼、還差什麼」，不要求商家重新把內容填進另一套資料庫。

素材狀態：REQUESTED → RECEIVED → CHECKED → CLARIFYING／READY_FOR_REVIEW → APPROVED → AVAILABLE；另有 REJECTED、REVOKED、EXPIRED。收到照片不是自動取得所有渠道使用權，商家對資料的回覆也不是自動核准公開。

### 每份素材應帶的資訊

原始檔、來源、提供者、適用服務版本、拍攝／製作時間、主張依據、人物或其他權利確認、允許渠道／語言／用途、到期日、衍生檔與核准紀錄。檔案先做類型及惡意內容檢查，對外連結不得存取內網資源。

AI 可整理、翻譯、編排及提出補拍建議，但不把合成畫面當成實際場地或服務證據；客戶客訴照片和逐字稿也不能直接變成行銷素材。未具備必要權利時保留草稿，或使用已授權的其他素材。

## 08｜真的操作渠道：上架、調整、訂單與售後

| 能力 | 執行內容 | 完成證據 |
| --- | --- | --- |
| 商品管理 | 建立草稿、服務版本、圖片、語言、包含項目、選項與規則；核准後建立或修改。 | 外部商品 ID、讀回欄位與核准版本對應。 |
| 銷售安排 | 設定已授權的價格、時段、渠道範圍；上架、暫停或下架；檢查共用資源。 | 發布狀態及實際可售查詢；不以 API 收件成功當成已上線。 |
| 訂單管理 | 匯入與對應訂單、確認、改期、取消、退款申請、憑證與核銷；依各來源能力執行。 | 外部訂單與金流狀態一致；通知由指定主體發送。 |
| 渠道營運 | 同步差異檢查、發布失敗修復、訂單漏件偵測與結算核對。 | 仍未完成的部分列出責任人、原因與期限，不假稱全部完成。 |

### 三種執行接法，必須在同一工作中心看得見

第一優先：正式 API 或既有系統的官方渠道功能。第二選項：經商家授權且平台允許的受控瀏覽器操作；使用預先設定操作路徑、變更預覽與結果驗證。第三選項：產生可直接執行的預填任務，交由商家或付費代營運人員處理。

瀏覽器接法不是繞過介面權限的方法；遇到多因素驗證、驗證碼或不受允許的操作時交回授權人員，不嘗試規避。頁面結構改變時停止受影響寫入，其他渠道繼續運作。人工完成的步驟要記工時，不列入全自動成功率。

### 先檢查個別能力，不用品牌名稱代替測試

商品修改、價格修改、庫存、訂單、退款及通知分別登錄權限與可用能力。rezio／KKday 的供貨型與連結型維護方式不同；連結型部分價格不會直接拋轉，不能把訂單同步當成內容與價格都同步。[R05]

渠道可能自行管理行前通知；例如 rezio 的 KKday 指引說明，KKday 來源訂單的通知不使用 rezio 信件樣板。通知的編輯權與發送權要納入渠道設定，避免以為改了自家模板就改到外部渠道。[R07]

每渠道保存 desired_version、submitted_version、observed_version、observed_at。外部仍在審核就顯示審核中；舊訂單保留原承諾，不因商品修訂自動變更。

## 09｜共用執行核心：案件負責到底

v1.0 的協調器與事件機制保留，但補上「長時間工作」的明確持久化狀態。語音、客訴、商家素材與渠道任務可以互相關聯，不需要每次由人重開一案。

| 共用元件 | 實作要求 |
| --- | --- |
| 案件與任務中心 | 每案保留 owner、scope、next_action、waiting_on、due_at、policy_ref、postcondition、cost_budget；跨入口經驗證後接續。 |
| 狀態與排程 | NEW → VALIDATING → READY → EXECUTING → VERIFYING → DONE；分支 WAITING、PARTIAL、UNKNOWN、ESCALATED、CANCELLED。外部事件或到期排程可喚醒任務。 |
| 授權與版本閘門 | 執行前檢查租戶、身分、用途、工具、資源版本、客戶同意／商家政策／本次核准。不可讓模型自己簽發有效核准。 |
| 可靠執行器 | 承接 v1.0 outbox／inbox、防重複動作及結果查詢；未知結果不盲目重試退款、訂位與商品建立。 |
| 結果驗證器 | 按動作定義完成條件：查單、查金流、讀回商品或正式審核狀態；無法驗證時保留未完成。 |
| 觀測與成本 | 記錄模型／提示／工具版本、每次嘗試、延遲、語音用量、人工分鐘及通知；逾時或風險觸發正確告警。 |

### 長時間處理不是讓模型一直開著

等待商家上傳照片、OTA 審核或退款結算時，狀態留在資料庫，任務停止占用對話模型。收到外部事件或到達設定檢查時間才喚醒。提醒合併並尊重聯絡權限；沒有回應時按政策更新等待或升級，不不斷發訊。

### 同一案件只有一個目前操作負責人

真人接手會更新責任版本，阻止尚未執行的 AI 動作；已送出的外部操作仍需查結果。不同角色可分工，但不允許兩個流程同時退款或覆寫同一商品。

電話回覆停止、任務取消、外部交易取消，都是不同事件。OpenAI 伺服器控制文件也要求單一動作責任與事件去重；語音主連線與後端同時看到事件時不得各執行一次。[R02]

## 11｜端到端示範：一項問題如何真的被處理與改善

以下全部為驗收用假設劇本，不是商家實績。示範使用一間既有客服與預約工具的茶體驗商家；標準服務為九十分鐘，現場語言方式已核准。

| 情節 | 系統應完成的工作 | 驗收證據 |
| --- | --- | --- |
| ① 海外旅客來電 | 確認兩人、指定日期及語言需求；覆誦並以安全付款方式完成預訂。 | voice_session、quote、客戶確認、原系統訂單與通知互相對應。 |
| ② 客戶提出語言落差客訴 | 驗證訂單，對照成交時渠道頁、商家服務版本與實際陳述，不用目前網頁取代歷史承諾。 | 客訴證據、原因狀態、可執行補救方案。 |
| ③ 完成補救 | 在已授權政策內執行客戶選擇；若由渠道收款，透過渠道流程並持續追蹤。 | 退款或其他補救的正式結果；未完成不得關案。 |
| ④ 與經營者討論 | 指出已確認的表述落差；另將短時長詢問列為測試假說，不與客訴混成同一原因。 | 有來源的觀察卡、商家回覆及擬變更內容。 |
| ⑤ 索取必要素材 | 請商家提供現場說明卡、短片及新版本內容；自動整理成可審閱的商品草案。 | material_request、素材來源與權利、服務版本差異。 |
| ⑥ 執行核准改版 | 檢查老師／場地共用，發布自有頁與授權渠道；外部審核中如實顯示。 | 各渠道 observed_version、商品／訂單對應、通知責任。 |
| ⑦ 管理後續訂單 | 新訂單使用新版；舊訂單照原承諾。比較完成交易、支援與補救成本。 | 訂單版本快照、渠道淨貢獻、再客訴與資料完整度。 |

### 同一輪中的「可以做」與「需要商家決定」

助理直接處理：查資料、安排標準預訂、核准政策內售後、主動索取缺少素材、準備變更與發布、檢查結果。經營者決定：新的服務承諾、價格、資源安排與超出授權的補救。核准後後續工作由助理執行，不再把整串工作丟回老闆。

一次展示必須含正常與失敗路徑：語音改口、退款尚未完成、素材權利未核准，以及一個渠道仍在審核。只演示全部成功不足以驗收。

### 三種角色指標不能只看使用量

語音：正確預訂完成、關鍵欄位修正、重複副作用、成功接手與每完成案件成本。客訴：補救完成時間、重開率、退款差異、升級品質與顧客回饋。經營：提案證據、商家補件時間、核准到實際上線時間、改版後交易／成本與客訴。

自動解決率以符合服務範圍的全部案件為分母，另列排除與轉人工原因。不得把機器人不回覆、客戶沒再說話或有人手動補救的案件，全部算作 AI 自動成功。

### 讓經營者主要提供專業與核准，助理執行其餘工作

### 收入與成本不能只按 token 計算

基礎接單與標準售後可作企業服務；即時語音依電話、音訊用量與包含額度計價；進階商品／渠道協作依範圍與連接數擴充。標準客服改善不拆成每次建議都收費；外部分銷報酬與工具服務另有依據。

成本記錄含電信通話與轉接、即時模型／轉錄／語音、音訊及附件處理、通知、背景查詢、連接維護及人工。按供應商實際計費口徑記錄，不把所有語音都當一樣便宜。重試、重送與平台錯誤不重複計為商家新案件。

自動受理與值班真人是不同承諾；服務時段、緊急責任人、轉接失敗及退款追蹤均須有人負責。缺少人力時如實設定接續安排，不宣稱已提供全年無休真人客服。
