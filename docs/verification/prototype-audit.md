# UX 原型核對與 UX 2.1 修訂紀錄

核對日期：2026-11-22（Asia/Taipei）

## 1. 本次交付

原始 UX 1.0、UX 2.0 原樣匯入。另以 UX 2.0 為底新增 UX 2.1，修正本次確認的三個互動問題。沒有新增後端、外部交易或正式授權機制。

| 版本 | 檔案 | 用途 |
| --- | --- | --- |
| UX 1.0 | [歷史原型](../../prototypes/merchant-assistant/ux-v1/index.html) | 保留較早的功能分頁與操作流程；不是目前商家首頁的開發依據 |
| UX 2.0 | [原始原型](../../prototypes/merchant-assistant/ux-v2/index.html) | 保留來源字節及原始行為，供追溯 |
| UX 2.1 | [本次修訂原型](../../prototypes/merchant-assistant/ux-v2.1/index.html) | 建議用來檢視商家互動；仍是本機模擬 |

原檔名稱分別為 `商家接單助理_UXUI_可點擊原型_UX-v1.0.html` 與 `商家接單助理_UX2.0_可操作原型.html`。原始來源校驗值列於 [匯入紀錄](../provenance/README.md)。

## 2. 實際存在的互動

UX 2.0 與 UX 2.1 都是單一示範商家的瀏覽器內狀態程式，主要展示以下六種情境：

| 情境 | 實際互動與限制 |
| --- | --- |
| 商家新增服務 | 討論短版 → 輸入說明 → 補素材 → 確認用途 → 審閱版本 → 核准 → 顯示兩個渠道各自的狀態 |
| 沒有需要商家決定的事 | 收起同一建議；仍顯示示範接單、退款的負責與處理狀態 |
| 超出政策的補救 | 原服務費已退的合成案例，另決定是否補貼交通費 NT$600；送出後仍顯示等待正式結果 |
| 渠道授權失效 | 官網進度保留，只請商家模擬重新授權合作旅宿；回到等待審核 |
| 外部結果完成 | 展示控制可將已核准、授權有效的發布改成已讀回確認；沒有真實外部回報 |
| 核准後修改 | 更新草案版號並清除目前核准；內容要重新核准 |

首頁另可檢視合成的語音預訂結果、規則內退款、自主範圍、真人接手與本機工作紀錄。暫停接單只切換示範狀態，不會停止任何商家的實際服務。

自由輸入沒有接 LLM。快速輸入只辨識「暫停接單」「今天／進度／回報」「短版／繼續」等預設分支；其他文字存成瀏覽器內的草稿。服務表單以固定規則擷取價格、分鐘、人數與時間，不能當作完整的自然語言需求理解。

## 3. UX 2.1 的三項修正

### 3.1 核准送出後不提前顯示成功

原始 `approve()` 先將兩個渠道設為 `pending`，經 900 毫秒的示範計時後，才把官網改成 `live`、合作旅宿改成 `review`。但原首頁在這段等待時間仍會顯示「官網已更新」。

UX 2.1 的首頁現在依兩個渠道的實際模擬狀態顯示：

| 狀態 | 顯示 |
| --- | --- |
| 官網尚未 `live` | 發布工作已接手，正在核對結果 |
| 官網 `live`、旅宿 `pending` | 官網已更新，旅宿端尚待核對 |
| 官網 `live`、旅宿 `review` | 官網已更新，旅宿端等待審核 |
| 兩者皆 `live` 且無待恢復授權 | 兩個入口都已核對完成 |

結果頁的每個渠道各自判斷狀態；整體 `all` 只用來決定完成標題與摘要，不再拿它決定單一渠道是否完成。改動也同步反映在首頁摘要、工作回報與執行憑據，避免不同入口對同一結果出現矛盾。

| 單一渠道狀態 | 顯示及證據語意 |
| --- | --- |
| `not_started` | 尚未開始；尚未建立發布工作 |
| `pending` | 核對中；已建立工作，但尚未確認外部受理或生效 |
| `review` | 待外部審核；已知對方正在審核，仍沒有生效證據 |
| `live` | 已生效；顯示該渠道自己的讀回結果 |
| 合作旅宿授權失效 | 需要授權；優先顯示恢復授權的需求，不顯示全部完成 |

因此 `pending/pending` 不會提前變成「對方審核中」，而 `pending/live` 也會保留合作旅宿已完成的結果，等待官網自己的核對。

### 3.2 服務內容保存商家原話

原表單雖接受不同的服務說明，卻只改價格、分鐘、人數等欄位，確認卡的內容仍保留固定茶品飲文字。例如輸入咖啡課程，確認卡仍可能出現兩款茶與茶點。

UX 2.1 將表單原話寫入 `facts.content`，並透過既有 `esc()` 顯示在確認卡；不自行假裝已解析或改寫商家的意思。價格、時長與容量仍由原本的簡單規則擷取。其他固定示範欄位仍應人工核對，這項修正沒有將原型變成通用需求理解系統。

### 3.3 阻擋零人容量

自然語言表單原先只檢查容量不可超過 8，會接受「最多 0 人」。UX 2.1 改為要求 1 至 8 人；沒有填容量時，仍沿用原示範值 6 人。這是示範資源設定，不是正式平台的全域容量規則。

為使新舊原型並存且互不覆蓋本機狀態，UX 2.1 使用獨立的 `merchant-ux21-v1` 儲存鍵，並更新畫面版本名稱與原型測試介面的版本值。未更動原始 UX 2.0 的儲存鍵或檔案。

## 4. 依賴與資料流

- 三份 HTML 的 CSS、JavaScript、圖示皆內嵌，沒有外部 JavaScript、CSS CDN、遠端字型或圖片依賴；可在本機以靜態檔案伺服器開啟。
- 未發現 `fetch`、`XMLHttpRequest`、`WebSocket`、`sendBeacon` 或外部表單送出路徑。語音、付款、退款、發布與登入授權皆為模擬，沒有真實副作用。
- UX 1.0 以 URL fragment 在同一份 HTML 切換畫面，狀態在記憶體內；沒有使用 `localStorage`。
- UX 2.x 使用 `localStorage` 保存草稿、示範狀態、核准版號、工作紀錄與使用者所選檔案的名稱等中繼資訊。
- 所選本機素材上限為 25 MiB；圖片透過 `URL.createObjectURL` 預覽。檔案內容沒有上傳，blob URL 不會持久保存。重新整理後，尚未核准的素材會要求重新選取。
- 自由文字與檔名在 HTML 插入前經跳脫處理。本次另外核對服務內容包含 HTML 字串時，確認卡顯示的是文字。

## 5. 驗證方式與結果

本次完整閱讀 UX 2.0 的 HTML／JavaScript，檢查 UX 1.0 的資源與網路路徑，並對 UX 1.0、2.0、2.1 抽出完整內嵌腳本執行 `node --check`。三份腳本均通過語法檢查。

另外以 Node 的 `vm` 執行原始腳本，提供最小 DOM、計時器與 `localStorage` 替身，檢查確切的狀態變化。UX 2.1 的 18 項程式檢查均通過，另記錄兩個保留限制。這是程式層的模擬驗證，**不是瀏覽器畫面、點擊或無障礙實測**。

HerdR 可在 repository 根目錄重跑同一組檢查：

```sh
node tests/prototype-regression.cjs
```

[驗證腳本](../../tests/prototype-regression.cjs) 只使用 Node 標準庫，直接讀取 UX 2.1 HTML 的內嵌腳本；路徑以測試檔所在目錄解析，不依賴特定工作目錄或套件安裝。本次以 Node `v24.22.3` 執行，結果為 **18 項通過、0 項失敗，退出碼 0**；檢查失敗會以非零退出碼結束。計時器未恢復及補救卡旗標兩項限制另列為 `observations`，不計入 18 項通過結果，也不要求未來修訂保留這些限制。

## 6. 保留的原型限制

1. **刷新不會恢復執行中的計時器。** 在 900 毫秒示範執行期間重新整理，雖可恢復 `executing/pending` 狀態，卻沒有背景工作接著執行。正式系統須由伺服器工作流程與結果查核處理。原型可用情境導覽重設或模擬結果，不應據此推定有耐久執行能力。
2. **補救核准不是客訴結案。** `exceptionResolved=true` 在原程式中僅用來收起補救決策卡；畫面仍寫明等待正式結果。此欄位不可直接移植為後端 Case 的解決或結案狀態。
3. **版本與證據只是示範值。** 核准只有本機版號與時間，沒有正式批准者、授權範圍驗證、內容 hash、不可變紀錄或外部結果證據。
4. **沒有通用多工作管理。** 原型圍繞一件服務變更及少量固定情境，沒有後端 Work／Case／Execution 資料模型、多人並行控制、租戶隔離或任務排程。
5. **沒有完整的外部未知結果流程。** 合作旅宿的 `review` 是已知待審核；授權失效是另一個明確情境。原型沒有獨立模擬「寫入是否成功無法確定」的 `UNKNOWN` 與 reconciliation 契約。

## 7. 與後續 Work／Credit 設計的差異

原始 UX 2.0 的例外補救是交通費 NT$600，不是後續工程報告提到的 NT$500 Credit。UX 2.1 保留這個情境，沒有假裝新增 Credit 發放引擎。

後續 Work、ApprovalRecord、AuthorizationDecision、CompletionEvidence、Credit／Refund ledger、外部 connector 與耐久工作流程應依 [SD 文件](../sd/README.md) 實作。不能從原型中的成功訊息反推後端已完成，也不能把固定示範金額當作商家的正式授權政策。

## 8. 原始文件內容檢查

針對本次取回的 12 份來源文件，檢查 HTML 全文、DOCX 正文及文件屬性，以及 PDF 可抽取文字，未發現下列模式：私鑰區塊、常見 GitHub／模型服務 token、AWS key ID、Email、台灣手機號碼或台灣身分證號格式。

畫面與原型程式中的人名代稱、商家、訂單編號、金額與營運數字均以示例／合成資料標示。這是指定模式的文字掃描與內容核對，沒有對內嵌圖片逐張 OCR，也不是對任意未知憑證格式的完整資安稽核。

## 9. HerdR 延續要求

以 UX 2.1 檢視目前商家互動；以原始 UX 2.0 和匯入 manifest 追溯來源。正式前端應讓文字與核准、工作、外部結果的實際狀態一致，並補上本文件尚未覆蓋的真實瀏覽器驗證。

接上正式後端時，將「示範情境切換」「模擬授權完成」「模擬外部結果」與商家日常操作分離。對產品使用者顯示需要他提供的資訊、需要他作出的決策及實際完成結果；不要求商家逐步操作內部執行程序。
