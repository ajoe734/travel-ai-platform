從「操作後台」改成
「交代事情，收到結果」。
保留 AI 真正接單、處理客訴、討論服務、索取素材及管理渠道的能力；把例行操作從經
營者的畫面與工作清單一起移走。

   不是把八個選單藏進聊天框，而是改變工作責任：
   經營者提供新事實、作必要決策；AI 組織後續工作、執行、追蹤並核對。

 經營者需要參與                     不應要求經營者例行操作
 說明新服務的真實內容與資源               每一筆查價、查位、建立訂單與確認收款
 核准新價格、承諾、素材用途與              依核准政策可處理的標準改期、退款與通知
 例外補救
 恢復只有本人能恢復的登入權限              逐渠道重填商品、盯審核或修復一般 API 重試

  一個主要入口                                   按需打開詳情
  需要你＋簡短工作回報＋可隨時交代的對話。原有通訊                 訂單、證據、執行紀錄與手動接手仍存在。它們是查詢
  工具也可承載這些卡片，不另建每日必登入的龐大後                  與例外處理能力，不是老闆的日常步驟。
  台。

01 / 日常入口

首頁只回答：現在需要我嗎？




① 一項必要判斷：新的服務內容與價格，由經營者決定。
② 例行工作在執行：語音接單與規則內退款不變成人工待辦。
③ 證據按需展開：數字、逐字稿與外部狀態可以查，但不強迫巡查。
正式多案情境須按風險與期限排序，明示其他必要事項；不能為了首屏乾淨而隱藏緊急事件。原型以一項決策展示分工。

03 / 正常流程不要求經營者按確認

標準接單與售後，讓 AI 做到底。




  旅客語音／文字 → 確認需求 → 查價與查位 → 客戶確認 → 預訂及付款 → 正式核對 → 交付

04 / 討論與素材接續

不請老闆填資料庫，只補這次缺的。




沿用：已有且可用的服務資料、照片與規則，不再重問。
只索取：這次新增服務需要的英文說明卡；可用原本方便的檔案形式。
兩件事分開：收到檔案不等於取得對外使用權，核准用途後才進入發布草案。
原型支援本機檔案選擇與預覽，不上傳或判讀內容。正式流程仍需檔案檢核、來源、素材用途與版本關聯。

06 / 發布與結果驗證

等待外部，不等於等待老闆。




明確區分：官網已生效；合作旅宿仍在審核，不能標示全數完成。
工作仍有負責人：由助理繼續追蹤；不要求經營者重按發布。
需要人時再提出請求：登入失效才請本人重新授權，恢復後只接續未完成的部分。
頁面中的狀態來自本機模擬。實際產品須以正式事件、查單與讀回證據推進，不能以倒數或畫面動畫冒充外部完成。

09 / 開發與驗收責任

不能只把工作藏起來，要真的少做。
 要實作的行為                      驗收判準
 首頁的注意事項路由                   區分需要經營者、等待外部、平台維運與已授權自動處理。
 一項委託跨步驟接續                   口述、素材、核准、渠道任務同案接續，不要求換頁重填。
 批次合併與風險排序                   同一工作只請求一次必要介入；緊急安全事件不得被摘要隱藏。
 版本與一次核准                     內容改變使舊核准失效；新版本不得偷偷修改既有訂單。
 重新授權與失敗恢復                   已完成工作保留；不重建商品或重發副作用。
 暫停、修正與真人接手                  可介入但不需全程監看；停止新接單不停止必要退款及通知。
 合併回報與延後                     維持原方案後，不以相同證據反覆要求討論。
 真實成本與結果                     紀錄經營者＋平台人員兩邊工時，不能把工作轉嫁給另一方。


   設計目標
   標準接單、規則內改退：經營者零操作。
   新服務：只參與必要說明、素材及決策。
   這是驗收方向，不是已證實的節省時間或成交提升。

仍需真人測試的任務
讓實際經營者完成：查看是否需要自己、拒絕一項建議、提供缺少素材、修正價格、核准、離開後接續、判斷外
部待審、恢復授權。觀察理解錯誤、工作時間及不必要的中斷，不只詢問「畫面好不好看」。

怎麼使用這個交付
開啟 index.html → 從「一起確認內容」走完整流程。右上「切換示範情境」是展示控制，不是商家產品選單。
自由輸入未接 AI，未知指令僅保留本機草稿；不輸入真實個資、密碼或卡號。
